## End-to-end CLI

```text
$ marqdo run examples/memory-buffer.mq.md --json
{"success": true, "value": {"type": "int", "decimal": "141"}, ...}

$ marqdo run examples/memory-buffer.mq.md --max-memory 0 --json
{"success": false, "error": {"code": "resource.exhausted", ...}, ...}
```

The example creates one 64 KiB page with a declared maximum of four pages,
writes two bytes through two names that share one region, and returns
`42 + 99 = 141`.

## Fixtures

Semantic goldens:

* `tests/conformance/semantics/45-memory-buffer.mq.md` — shared identity
  (`另一个名字 = 区域`) and two byte writes.
* `tests/conformance/semantics/46-memory-grow-zero-fill.mq.md` — zero-page
  create, `grow` returning the old count, old bytes preserved, new byte zero,
  `memory.size`.
* `tests/conformance/semantics/47-memory-isolation-and-alias.mq.md` — two
  regions do not alias at the same offset; handle equality is identity.

## What this does not prove

* No `.mq.md` stdlib repository or allocator/closure fixture yet (RFC-CM P2).
* No `Resource`, `Stream`, byte-transfer ABI, stdlib `print` migration or
  `Table` storage abstraction (P3–P5).
* No Windows/macOS evidence and no remote CI URL.
* No claim of block-level memory safety for a user-written allocator; the
  runtime only bounds each access to its region.
* No claim that `strict` accepts new I/O: memory is pure computation and no
  `HostOp` or provider was added.
