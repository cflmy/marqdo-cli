# RFC-CM-0001：Marqdo 自主计算机器、可寻址内存与系统交互边界

> **状态**：设计提案（Draft，未实施，未批准）  
> **日期**：2026-11-20  
> **建议归档路径**：`docs/architecture/RFC-CM-0001-compute-machine.md`

## 摘要

Marqdo 的优势不应只是用 Markdown 排版代码，而应是：在不更换 Markdown 语法角色的前提下，以**自身定义的计算语义**构造算法、数据结构、运行时工具和知识制品。现有解释器已提供整数、浮点、文本、列表、映射、控制流和函数调用，但尚未提供**由 Marqdo 程序控制的可寻址字节存储**；其赋值左侧仅支持标识符，系统交互集中在一组固定 `HostOp` 与外部插件能力中。这妨碍了用 `.mq.md` 自己编写内存分配器、二进制协议、共享节点结构、虚拟机器等低层算法。

**提议：以“托管值 + 多个可增长的线性内存区域 + 不透明系统资源”为计算机器的三个基础领域。**

1. 保留现有 `Value` 计算体系，不强迫一切数据都变成字节地址。
2. 引入一个拥有独立身份、按字节索引、可增长、具有边界的 `Memory` 值；每个区域内部线性寻址，物理实现可以是 Vec、分页或其他表示。
3. 扩展现有“位置赋值”：允许对适当的索引目标写入，如 `m[8] = 42`，而不是另创 Markdown 语法或几十个关键字。
4. 为创建、测量和增长内存定义**极少量计算原语**；让 `malloc/free`、内存池、链表、编码、缓冲区等**首先在 `.mq.md` 标准库**中实现。
5. 将终端、文件、网络、进程、设备定义为**外部资源**，经稳定、可授权、可替换的底层适配接口交互；Marqdo 自身可以实现高级系统库与协议，但系统调用或硬件访问的**最后一步不能凭空消失**。
6. CPU 寄存器由解释器/编译后端管理；裸机器码、GPU/QPU、共享内存原子操作暂不进入本 RFC 的基础语义。

这是一种**可编程的抽象机器**，而不是“在每种新需求前追加 Rust Host 函数”的框架，也不是把 x86/RISC-V 指令直接变成 Markdown 语法。

## 1. 设计动机：究竟希望解决什么

### 1.1 真实诉求

Marqdo 必须能在不借助 Python、JavaScript 或宿主语言提供专门算法函数的前提下，**通过自己的控制流和基础存储机制**构造原先不存在的高级能力。例如：实现内存分配器、二叉树、哈希表、字节码解释器、文件格式解析器、数值算法。对于 OS 和硬件，要求的是**高级功能主要由 Marqdo 实现，底层权限与系统调用接口保持稳定**，而不是“所有跨越内核边界的指令都神奇地由 Markdown 自己完成”。

### 1.2 非目标

- 不追求复刻 CPU 的真实寄存器、指令流水线、页表与异常处理体系。
- 不把所有 Markdown `[]()` 链接重新定义为动态指针。链接继续表示文档/符号寻址，不伪装运行时对象地址。
- 不把 GFM 表格当成实际运行内存。表格可以用于数据/状态的可读表达与快照，但不是存储管理器。
- 不要求标准库全部使用 `.mq.md`；原生加速可以有，但**不是实现一般算法的必要条件**。
- 不在第一期承诺用户代码内存安全、数据竞争自由、GPU 加速或跨平台无差异系统调用。
- 不支持在无权限环境中直接执行任意机器码或任意 syscall。

### 1.3 设计原则

**P1 语义最小而充分**：首先增加无法由现有表达式自然实现的基础机制，不先增加高级 API 或新关键词。  
**P2 高级能力在语言中生长**：新增算法/数据结构不修改解释器、不修改 `HostOp`、不需要重新编译 CLI。  
**P3 读写位置统一**：索引读取和索引赋值遵循同一类“位置”语义；`Memory` 的读取/写入是基础例子，普通列表的值语义不得无声改变。  
**P4 内外边界诚实**：内存操作是语言计算；操作系统 I/O 依赖权限、平台接口和底层实现。  
**P5 可读性**：普通 Markdown 文档仍然可读；`##`/`**`/`*`/列表/blockquote 的现有角色不因本 RFC 改变。  
**P6 安全与可验证性**：将可验证的保证限定在区域边界和权限边界；不对自定义分配器的块级错误作虚假保证。  
**P7 零隐式权限**：能够导入模块、持有字符串或解析文档，不代表拥有文件、网络或设备访问权。

## 3. 总体架构与唯一的语义边界

```text
  .mq.md 文档    GFM Table/Link/标题/正文仍按 Markdown 正常渲染
       │
       ▼
  Canonical Markdown AST ──▶ 已有 Frontend ──▶ Marqdo IR
                                                   │
                               ┌───────────────────┤
                               ▼                   ▼
                           值与控制            存储与位置
                           Int/List/Map          MemoryRegion
                           函数/赋值/循环         字节读写/增长
                               └─────────┬─────────┘
                                         │
                                Marqdo 计算核心
                                         │
                      需要访问外部世界时才穿越边界
                                         ▼
                           Resource capability gate
                              │       │        │
                          console    file    network/device
                              │       │        │
                         Platform Adapter / OS ABI
```

逻辑上的执行状态可以表述为：

`State = (Control, Frames, ManagedValues, RegionStore, ResourceTable, Budget)`。

- `Control`：当前 IR 节点和执行顺序；保留已有控制流。
- `Frames/ManagedValues`：现有 `Value`、局部变量和调用语义。
- `RegionStore`：一组可增长字节区域，每个区域按 `(region identity, offset)` 寻址。
- `ResourceTable`：操作系统资源的不透明句柄与授权信息，**不得与内存地址混用**。
- `Budget`：fuel、调用深度、内存限额、I/O 限额、截止时间等。

此设计**不规定**必须先创建自定义字节码 VM。现有树遍历解释器可直接执行新内存语义；将来引入字节码、JIT、LLVM/Cranelift 等属于可选执行方式，必须保持可观察语义。

## 4. 三种基础领域：值、内存、资源

### 4.1 托管值：维持已有语义

`Int/Text/List/Map/Table/Formula/Code` 等继续是运行时管理的值。普通 `b = a` 不得偷偷将普通列表变成共享可变指针。现有对象可以由 Rust 分配内存——**实现语言不等于语言语义**。这个领域负责易用性、文档处理、不可变数据等。

### 4.2 Memory：拥有身份的字节区域

新增 `Value::Memory`（名称暂定），含不可伪造的运行时区域引用。逻辑区域内部是一串字节，下标为非负整数；不同区域即使下标相同也不是同一个位置。

- **区域身份**：由本次运行中的内存实例签发；`Memory` 复制/传参时保留指向相同区域的身份（共享，不复制所有字节）。
- **地址**：`(MemoryHandle, offset)`；`offset` 只在所属区域内有意义；整数本身不是获得其他区域权限的凭据。
- **内容**：每个元素是 `0..255` 的一个字节；初始字节为 0。
- **大小**：区域长度是页大小的整数倍；建议初期采用 `64 KiB` 页，以简化语义与工具链对照，不要求底层真的按页分配。
- **增长**：只增长，不缩小；旧地址偏移不变；新加入的字节全部为零；不得突破区域/运行全局限额。
- **读取**：`m[i] -> Int(0..255)`；越界、非法整数或已失效区域均是类型/存储错误。
- **写入**：`m[i] = b`，`b` 必须是 0..255 的整数，不隐式截断；越界拒绝。
- **相等性**：两个 Memory 引用的相等比较区域身份；不比较全部字节；Memory 不定义大小排序。
- **序列化**：不允许将活动 `Memory` 句柄伪装成数值或跨进程永久有效地址。允许显式**复制字节内容**为快照，需限额；跨进程传输需要显式复制或另立经过授权的共享内存协议。
- **生命周期**：第一版只在单次执行内存在；由 Runtime 保持活动句柄可达性，引用消失后可回收，至少在运行结束时回收全部区域。**不增加用户可见的 `free(region)`**，以免引入悬空区域句柄。用户的 `malloc/free` 管理的是**区域内部的块**。
- **内存安全范围**：Runtime 保证单次操作不访问该 Memory 区域之外；不保证用户自编分配器不会越块、重复 free、释放后复用错误。

此设计不要求新增独立的 `Pointer` 原始类型。**首版指针可由 `Memory` 引用和 `offset` 组合表达**；是否将这一对优化为一等 `Pointer`，由实际性能与调用需求决定，而非现在先引入语法。

### 4.3 Resource：与外部世界交互的独立对象

`ResourceHandle` 是由可信平台/Provider 签发的不透明句柄，代表文件、控制台流、网络连接或专门设备；含授权访问模式与生命周期。**它不是 `Memory`，不能索引成任意 RAM，也不能通过伪造整数创建。**

其常见操作是 `open/read/write/close`，但具体合法操作取决于资源接口。操作系统错误、EOF、部分读写、超时、取消都需要保留独立结果和错误语义。不得假定一次 `read` 总能填满缓冲区、一次 `write` 总能输出所有字节。

### 4.4 为什么要划分，而不是单一“万能地址空间”

`Memory` 代表运行时可管理的存储；`Resource` 代表外部效果。普通内存读写是局部状态改变，终端输入/网络读取可能随外部世界变化。把二者统一为可以随意解引用的指针，会隐藏权限和不可重复性，也会使知识证明与回放语义失真。

## 5. 可编程动态内存：到底哪些必须内置

### 5.1 最小计算内核操作

这里定义**能力**，不冻结最终函数名：

| 基本能力 | 候选用户接口 | 运行时职责 |
|---|---|---|
| 创建区域 | `memory.new(initial_pages, max_pages)` | 签发不可伪造引用，检查预算并分配零初始化区域 |
| 查询大小 | `memory.size(m)` | 返回页数，不泄露真实宿主指针 |
| 增长区域 | `memory.grow(m, pages)` | 原有字节与偏移不变，新字节为零；成功返回原页数，失败返回可区分错误 |
| 读取一字节 | `m[i]` | 边界检查，读取 `0..255` |
| 写入一字节 | `m[i] = b` | 边界和值域检查，更新同一 Memory 区域 |

`memory.new/size/grow` 是操作而非关键词；`m[i]` 利用当前已有的读取表达式，`m[i] = b` 只扩展现有赋值目标语义。这是此 RFC 要求的**唯一用户可见表达式语法增量**。

`len(m)` 可在另一个 ADR 中统一成字节长度而非另设 `memory.size`；这里暂不混淆“页数”和“字节数”。是否以页或字节为 `grow` 单位也应通过 ADR 固定，本文的原型推荐页。

### 5.2 位置赋值（Place）如何实现

对左值 `x` 与 `m[i]`，**赋值含义不同但遵循一个语法规则**：

- `x = value`：仍重新绑定当前函数帧局部变量，现有语义不变。
- `m[i] = byte`：先按既有从左到右顺序求值 `m` 与 `i`，检查目标为 `Memory` 并检查偏移和值，然后更新同一内存实例。
- `list[i] = value`：**不在第一个阶段承诺**。是否将列表修改为值更新/可变对象更新，要另行定义，不能顺便改变现有列表复制与索引语义。
- `obj.field = value`：首版也不必实现。只有在明确记录值/对象语义后再拓展。

表达式编译结构的最小增量是 `Assign { target: PlaceExpr, value: Expr }`，其中 `PlaceExpr` 初期只有 `Local(name)`、`Index(base,index)`；索引目标仅接受 Memory，其他索引仍只读。无需新 Markdown 节点。

### 5.3 自定义指针与分配器

`malloc(n)` 在 `.mq.md` 标准库里持有一个区域 `m` 和元数据指针 `next`，向调用方返回区域内偏移（或 `{region:m, offset:p}` 组合值）。`free` 仅将已分配块放回空闲链表；若空间不足，调用 `memory.grow`。对齐、大小、空闲块链表、合并策略都由 `.mq.md` 编写，**不要求 Rust 为每一种分配算法做特殊 HostOp**。

例：块格式 `[size:u32][next:u32][flags:u8][payload...]`。首版只支持按字节读取，`u32` 的编码/解码可以使用四次索引、`//` 和 `%` 在 `.mq.md` 中实现。若该路径确实过慢，后来可增加 `load_u32` 等**语义等价、可验证的加速实现**，不能因此把完整分配器写到 Host。

分配器可建立：Arena、first-fit、buddy、slab、链表/图、字符串字节编码、编译器符号表、虚拟 CPU 的寄存器文件等。**内存块的逻辑安全由标准库分配器定义**；调用者拿到任意偏移后仍有越块写的能力，这属于明确的低层风险。

### 5.4 内存模型形式定义（草案）

令 `R` 是区域身份集合，`M[r]` 是 r 区域的字节序列，`len(M[r])` 是其有效长度。

- `read(r,i) = M[r][i]`，前提 `0 ≤ i < len(M[r])`。
- `write(r,i,b)` 将 `M[r][i]` 更新为 `b`，前提 `0 ≤ b < 256` 且 `i` 合法；其余字节不变。
- `grow(r,k)` 要求 `k ≥ 0`，若预算允许，尾部追加 `k × PAGE` 个零字节，旧位置的字节值不变；否则返回显式失败且区域不变。
- 不同区域互不别名：`r1 != r2` 意味着修改 `M[r1]` 不影响 `M[r2]`。
- `m2 = m1` 若 m1 为 Memory，则二者指向同一 `r`；若为普通 `List`，原有值语义不变。

实现必须防止巨大 BigInt 偏移到 `usize` 转换时溢出、`offset + length` 整数溢出、预算计算溢出。任何错误不得 panic、越界读写或产生非确定性内存破坏。

## 6. 非线性存储、寄存器与加速的恰当位置

### 6.1 非线性内存不需要独立关键字

- **逻辑非线性结构**（链表、树、图）：在一个或多个字节区域中存储偏移/引用即可；不要求新类型。
- **物理非连续内存**：运行时可以用分页、稀疏映射或 Vec 实现同一线性语义；用户无需知道物理页布局。
- **多设备内存**：未来可能带有设备特定权限与同步约束；不要将 CPU 内存随意解释成 GPU/QPU 地址。优先经专用受控资源/后端接入。

### 6.2 不加入真实 CPU 寄存器接口

当前局部变量与表达式临时值已经构成“虚拟寄存器”意义上的计算槽。编译到机器码时，可以由后端分配硬件寄存器。用户要模拟寄存器堆，可以用 Memory 自己实现；特殊硬件寄存器则是设备 I/O，而不是普通变量。

### 6.3 并行和原子操作

本 RFC 的内存规则初始定义为**单线程或按明确顺序执行**。绝不能声称 `m[i] = m[i]+1` 在多线程之间自动原子。未来若允许多个执行任务共享 Memory，必须另行设计同步/原子操作、数据竞争行为和访问序；也可以先采用无共享可变内存的任务隔离。新增原语应依据不可由当前操作正确组合而来的能力，而非先堆锁/屏障关键字。

### 6.4 GPU/QPU 不由普通 Memory 自动获得

Memory 支持字节缓冲区与数据布局，但 GPU 计算仍需要执行后端与数据传输，真实量子资源则不是可随意读取的字节地址。Marqdo 可用独立后端/服务处理硬件特有语义，内核应保持硬件无关。

## 7. 系统交互：能否不依赖 Rust/Python 实现高级功能？

### 7.1 必须给出的诚实答案

**可以**：大量系统功能由 Marqdo 标准库直接编写，包括文本与字节编码、目录遍历算法、协议解析、HTTP 报文、部分网络协议逻辑、缓存、日志格式、CLI 交互逻辑、文件格式读写、数据库协议客户端中的高层逻辑。程序运行时无需执行 Python 或 JavaScript，也不需要为每个高级库函数增加 Rust 分支。

**不能无条件做到**：如果当前运行方式是一个 Rust 编写的解释器，那么跨越用户态与操作系统的**最后一步**必须由解释器内建的系统适配器、已授权插件/worker、或其他可信底层机器代码执行。Markdown 源码不能在无相应运行环境、系统调用 ABI 和权限的情况下直接控制硬件。即使将来 Marqdo 编译成独立原生二进制，它也仍通过操作系统 ABI 或设备驱动与外界交互，只是**不再需要 Rust 解释器常驻运行**。

**不可混淆的四种独立性：**

| 层面 | 能否达到 | 含义 |
|---|---|---|
| A. 算法独立 | **可以，近期目标** | 排序、内存分配、解析器等算法均在 `.mq.md` 中 |
| B. 标准库独立 | **可以，近期目标** | 新标准库函数不修改 Rust Runtime/HostOp，单独版本发布 |
| C. 系统接口独立 | **有条件可以** | 已有的 OS 原语/权限可组合构造新功能；新增设备/OS 原语需相应适配器，但不改语言核心 |
| D. 运行时/宿主实现独立 | **中长期目标** | 独立编译成机器码/Wasm、或自举解释器，不依赖 Rust 解释器运行；仍依赖 OS ABI/硬件 |

**这里的“无需修改宿主”不是“无底层实现”。** 应将“高级逻辑用 Marqdo 实现”与“最后一跳由可信 OS adapter 执行”区分清楚。

### 7.2 最小系统资源操作模型

建议**不增加任何 I/O 关键字**，而以可注册、版本化的 `Resource` 接口提供 OS 能力。候选调用形式（未实施）：

- `resource.open(kind, descriptor, rights) -> ResourceHandle`
- `resource.read(handle, memory, offset, max_bytes) -> count | EOF/error`
- `resource.write(handle, memory, offset, bytes) -> count | error`
- `resource.close(handle) -> Result`

其中：

1. `kind` 例如 `stdio`、`file`、`socket`，必须由可信平台适配器或已安装的 Provider 明确注册，**不能因为传入任意字符串就自动获得能力**。
2. `descriptor` 是声明请求的结构化参数，例如项目内文件名、网络目标，必须验证并授权；绝非任意可解引用真实指针。
3. `rights` 是请求的权能；实际授权为“请求 ∩ 操作者 grant ∩ Provider 支持”，拒绝必须显式报错。
4. `read/write` 通过 Memory 区域交换原始字节，边界检查和缓冲区借用由 Runtime/Adapter 保证；不得允许 I/O Adapter 长期保存未固定的宿主 Rust 指针。
5. 区分 EOF/0 字节暂时无进展/取消/系统错误；支持部分读写，标准库负责重试与缓冲。
6. `close` 撤销对应资源句柄；已关闭句柄、重用 ID 必须借助 generation/注册表检查，不能错误访问新资源。
7. 对设备特殊操作，不强行滥用 `read/write`：必要时可由具体 Provider 暴露专门的**版本化、授权操作**；不在通用内核中新增一个无条件允许任意 syscall 的 `control` 后门。

`resource.*` 属于**平台接口层**而不是纯计算内核；即使调用看起来是普通函数，执行前必须检查权限。现有 Host 能力检查可成为迁移入口，但不应为每个新高层标准库函数创建新的 `HostOp` 变体。

### 7.3 应该怎样真正避免“每扩展一次就修改 Host”？

将目前的固定分派进一步分成：

```text
普通 Marqdo 标准库函数
       ├── 调用 Marqdo 语言计算原语（无需 Host）
       └── 仅在外部交互时使用稳定的 Resource ABI
                          │
                       Capability Gate
                          │
                   Provider/Platform Registry
                          │
         ┌────────────────┴───────────────┐
         ▼                                ▼
     标准平台适配器                    独立第三方 Provider
     文件/终端/网络                        新设备/专用系统能力
```

关键是**一次性稳定可扩展的外部操作契约**，而不是一张不断增长的 Host 功能目录。

现有 C ABI v1、worker 与 `CallableRegistry` 应先尽量复用；新接口可在不破坏 v1 的条件下增补版本化注册信息。如需升级，必须有兼容矩阵与迁移机制。**Provider 负责它新增的原始能力；`.mq.md` 标准库负责高级功能。**

### 7.4 两种系统访问路线及取舍

| 路线 | 优点 | 风险/限制 | 建议 |
|---|---|---|---|
| 能力化 `Resource` ABI | 统一权限与跨平台行为；适合安全分层 | 新的真正 OS 原语仍需要 Adapter/Provider | **默认且必须支持** |
| 直接的原生 syscall/FFI 边界 | 能较快覆盖大量平台特性 | 平台/ABI 依赖、地址搬运、权限绕过、维护和可验证性问题 | 仅可信、本机、显式授权的可选高级接口；默认 pure/strict 禁止 |

在 Linux 等平台，即使“直接 syscall”，也要处理目标架构调用约定、数字差异、结构体布局、指针与长度、errno 以及 OS 策略；Windows/macOS 并不提供与 Linux 一模一样的 syscall ABI。不得将其伪装成普适的语言核心。

**无悖论地满足用户目标的办法**：向 Marqdo 暴露一个小而稳定的**操作系统能力边界**，然后让标准库以 Marqdo 自己的程序逻辑组合出系统高级功能。这是可实现的强独立性；完全消灭系统边界不是现实目标。

### 7.5 端到端例子 A：完全用 Marqdo 构建交互式 CLI

**先决条件**：可信平台适配器提供 stdin/stdout 的已授权资源，Marqdo 运行时支持 Memory 操作。

1. 标准库 `io.read_line` 在 `.mq.md` 中申请/增长缓冲区，循环调用资源 `read`，查找换行字节。
2. 标准库 `text.utf8_decode` 用 `.mq.md` 处理 UTF-8（正确处理非法序列；编码策略可配置）。
3. 用户程序将文本解析为数字，用现有 `Int` 算术和条件循环处理。
4. 标准库 `io.write_text` 使用 `.mq.md` 的 UTF-8 编码，再经 `write` 输出字节。

**全流程无需 Python/Node，也不需要 Host 特地实现 `input()`。** 然而最底层 stdin/stdout 仍由 OS 适配器调用操作系统接口。

### 7.6 端到端例子 B：新增 HTTP 客户端能力

**先决条件**：系统适配器已经提供经授权的网络连接资源、DNS/地址解析的可用机制，以及必要的加密能力或可插拔 TLS Provider。

1. 标准库构造 HTTP 请求行、首部和消息体的字节序列。
2. 使用 `resource.write` 处理部分发送；使用 `resource.read` 实现缓冲接收。
3. `.mq.md` 解析状态行、首部、chunked 编码等；实现重试、缓存、超时逻辑。
4. 测试 HTTPS 时，必须使用可靠 TLS 实现（可由已审计 Provider 提供；“不依赖外部语言写协议逻辑”不意味着应该自己手写未经验证的 TLS）。

网络的“最后一跳”必须存在，且不同平台的 TCP/TLS 能力可能需要不同 Provider；不能只靠 Memory 推导出 socket。

### 7.7 端到端例子 C：科研加速与 QPU

- 经典数值模拟：`.mq.md` 可以在 Memory 中构造矩阵、压缩存储、数据布局算法，后续由独立计算后端加速。
- QPU：量子设备是具有权限、调度与门集约束的资源，不是普通 Memory；通过专用 Provider/Backend 提交计算、接收结果。
- 这种接口可保持标准库和上层代理/知识文档不绑定 Rust 宿主，但并不能保证算法自动获得 GPU/QPU 性能或精确的量子物理语义。

## 8. 安全、权限与错误模型

| 保护目标 | 首版保证 | 明确不能保证 |
|---|---|---|
| 虚拟 Memory | 区域越界、非法索引、增长限额、无效句柄失败 | 区域内 malloc/free 的块级内存安全 |
| 不透明 Resource | 授权身份、访问模式、资源关闭和 generation 检查 | 平台适配器/不可信原生插件本身绝对安全 |
| pure | 内部算术、内存与受预算控制的逻辑计算；不获得外部 I/O | 允许直接 syscall 或任意外部访问 |
| project | 对批准的文件/终端/网络资源进行操作，使用能力化 API | 等价于 OS 级进程沙箱 |
| strict | 维持现有 fail-closed 策略；新 I/O Provider 必须另行经过 OS 级安全验收 | 当前版本自动支持所有外部能力 |

进一步要求：

- 全局/单区域内存预算、增长次数与 fuel 限额、操作可取消性；内存失败不得半成功。
- 路径资源应使用受控根路径和可验证的 OS 打开策略，避免字符串检查后再打开造成 TOCTOU；网络权限需要处理名称解析/重绑定等问题。
- 插件/worker 不因拥有 API 名字自动获得权限；原生进程内插件不能被当作不可信沙盒。
- Memory/Resource 活动句柄不应直接跨线协议序列化；跨边界传输使用字节复制、快照或显式授权的资源传递协议。
- 诊断保持来源 Markdown 节点位置；可选追踪读取/写入的逻辑区域、偏移和长度，不能将外部文件秘密或原始敏感字节无条件写日志。

## 9. 与当前 Marqdo 语法和知识编译的结合

这一方案故意**只修改最少的表达式语义**。

- `##` 函数、`**` 执行、`*` 返回、Markdown 列表与引用规则继续维持规范。
- `[]()` 是**文档/知识的静态寻址**；动态 Memory 的字节偏移属于执行期位置，两者不强行共享 URI 语法。
- 普通 GFM 表格是文档值；可用于初始化/展示内存快照，但不会自动变成内存分配器。
- `memory.new(...)` 与 `resource.open(...)` 都可按普通函数调用表达；不新增 `memory`、`pointer`、`asm`、`register` 这样的语法关键字。
- 内存状态变化可选输出可读 GFM Table 供 View/Proof 使用；证明必须以抽象执行语义为依据，而不是假设表格文本本身就是执行存储。

示例（**候选语法，当前尚不可运行**）：

````markdown
## 研究一个字节缓冲区

此函数演示“可引用的存储区域”与普通 Markdown 叙述并存。

**区域 = memory.new(1, 4)**

**`区域[8] = 42`**

**另一个名字 = 区域**

**`另一个名字[9] = 99`**

*区域[8] + 区域[9]*
````

预期结果 141。注意这里 `另一个名字 = 区域` 分享 Memory 身份；一般列表/表格并不因此被改造成共享字节缓冲区。

## 10. 可行性和备选方案评定

| 设计 | 语言自主性 | 高层开发便利性 | 性能潜力 | 安全/复杂度 | 结论 |
|---|---|---|---|---|---|
| 继续只扩充 HostOp | 低 | 表面高 | 取决于 Rust 实现 | Host 随功能膨胀 | 否决为主要路线 |
| 只有托管对象堆/GC | 中 | 高 | 对一般数据不错 | 需要身份/生命周期语义 | 保留现有托管值，但不足以满足低层目标 |
| **多区域字节内存 + 托管值 + Resource** | **高** | **高** | 后端可优化，字节操作起初较慢 | 明确的区域边界；块级风险可见 | **推荐** |
| 任意裸指针 + 直接机器码 | 极低平台独立性 | 低 | 最高上限 | 高风险、难验证 | 只可选的可信原生扩展 |
| 纯 GFM 表格作堆内存 | 低至中 | 对展示很高 | 非常低 | 动态状态/身份混乱 | 否决 |

该推荐不是宣称“最优”已经被数学证明，而是在现有语法、实现成本、扩展性与安全边界下的**工程选择**。

## 11. CLI/Runtime/标准库仓库的具体职责

### 11.1 `marqdo-cli`：保留小而稳定的内核

- `marqdo-value`：新增不可伪造的 Memory 值表示；必要时添加 ResourceHandle，注意现有 PluginHandle 不能随意直接复用为 OS 资源句柄。
- `marqdo-expression`：`AssignTarget` 的 Local / Index 变体；保留原有表达式读取。
- `marqdo-frontend`：更新表达式 AST 对应 IR 和定位信息；不改变 Markdown 语义映射。
- `marqdo-runtime`：Memory 实例生命周期/增长/边界检查/预算；执行位置写入；参考解释器。
- `marqdo-host`：逐步提供可注册资源操作的能力边界；必须保持旧 `HostOp` 兼容窗口，不能一次砍断所有旧调用。
- `marqdo-package` / CLI：发布标准库兼容信息，继续利用已存在的 path/Git pinned lock；资源授权仍由真实操作者提供。

### 11.2 独立 `marqdo-stdlib`：以 Marqdo 实现通用功能

建议独立仓库 `cflmy/marqdo-stdlib`，首期目录：

```text
marqdo-stdlib/
  core/                  # 字节编码、整数工具、可恢复错误封装
  memory/                # arena, allocator, free-list, binary codecs
  collections/           # list/tree/graph/hashmap 等数据结构算法
  text/                  # UTF-8, parsing
  io/                    # buffered readers/writers, read_line
  data/                  # csv, json, 自定义格式
  tests/                 # 以 marqdo run/call 执行的标准库回归程序
```

高层函数应在 `.mq.md` 里，按普通模块导入。发行版携带一个经测试的 stdlib 版本，支持离线运行；单独发布更新时，要求明确的 Runtime 兼容范围与锁定。标准库可有原生加速 Provider，但不能把它作为常规功能的唯一实现路径。

### 11.3 独立 Platform Providers

系统 Adapter 可以由 Rust、C、汇编或将来的 Marqdo 原生编译代码实现。当前 CLI 不应为普通库函数增加 HostOp；对真正的新 OS 原语，若标准 Provider 不支持，用户必须安装/编写扩展 Provider，并获得相关权限。**不是每个新设备都能只靠修改 `.mq.md` 获得访问能力。**

## 12. 分阶段实施（范围严格受控）

### R0：冻结设计与当前基线（无新功能）

- 此 RFC 和对应 ADR 经审阅，确认 `Memory` 值语义、`index assignment`、错误类别、线协议边界及安全模式。
- 修复已有跨平台 CI/安全收敛问题；固定解释器行为的回归样例。
- 建立一页对照表：新增语义是否需要 `HostOp`、新关键字、新 Markdown 节点。首版目标均为“不需要”。

### R1：最小可寻址存储（核心里程碑）

- `Memory` 区域：创建、大小、增长、读取一字节、写入一字节；实现总/单区域预算、错误恢复与 trace。
- 支持 `**\`m[8] = 42\`**` 这类现有 Markdown 负载中的索引赋值。
- 不开放裸指针、不引入新寄存器、不改旧 List/Map/Table 的赋值与复制行为。
- 运行跨区域隔离与别名测试；报错不能导致原有区域被污染。

### R2：Marqdo 自举的内存与算法库

- `.mq.md` 顺序分配器；随后 free-list 可复用分配器。
- 不修改 Runtime/Host 编写并执行：可增长链表、二叉树、简单虚拟 CPU、UTF-8/二进制解析器。
- 提供内存利用率、分配吞吐、碎片率、执行时间及解释器 fuel 的测量；避免只用“功能跑通”证明成熟度。

### R3：最小系统资源闭环

- 在项目模式先实现 `stdio` 与受控项目文件的 `open/read/write/close`；**功能可用性不代表 strict 安全已通过**。
- `.mq.md` 标准库实现 `read_line`、`write_text`、文件二进制复制与 UTF-8 编码。
- 资源注册层允许 Provider 扩展；验证一个第三方资源端点不修改解释器编译即可接入（是否需要实现新的系统适配器需明示）。
- 对当前 `HostOp` 逐步适配，保留兼容期，不能强行把所有第三方都迁移到新的不成熟 ABI。

### R4：可选增强（不阻断基础版本）

- 索引/字段赋值的一般化、字节多宽度原语及位运算、快照、增量编译、优化执行器。
- 需要共享内存并行时，再设计原子/同步与数据竞争语义。
- 独立网络/TLS、设备、GPU、QPU 后端与原生编译目标。

**必须遵循的顺序**：R1 完整正确 → R2 验证计算自主性 → R3 证明外部交互可组合；不先把 R4 的设备能力和并发类型系统塞入 CLI。

## 13. 端到端验收清单

| 编号 | 验收项目 | 判定标准 |
|---|---|---|
| T1 | 语义一致性 | 旧的局部赋值与 List/Map/Table 行为完全不变，旧 Markdown AST golden 通过 |
| T2 | Memory 隔离 | `m1[0]=x` 不影响 `m2[0]`；`m2=m1` 后写入可相互观察 |
| T3 | 增长与错误 | 成功增长保留旧字节且新字节为 0；负索引、越界、超限增长、巨大 BigInt 均明确失败且不破坏状态 |
| T4 | 自建分配器 | `.mq.md` 实现 malloc/free，释放块重复利用；高低地址和碎片测试通过 |
| T5 | 高级数据结构 | 不改 Rust 核心，仅新增 `.mq.md` 实现可增长链表、树、二进制协议解析器 |
| T6 | 标准库独立升级 | 旧 CLI 二进制保持不变，安装一个与之兼容的新 `.mq.md` 库并成功使用 |
| T7 | 终端闭环 | `marqdo run` 仅使用标准库加基础 OS Adapter，完成多轮输入/输出，无 Python/Node 调用 |
| T8 | 系统资源授权 | 无 grant 无法 open；已关闭/伪造 handle 无法访问；项目路径无法越权；所有拒绝有诊断和必要审计 |
| T9 | 安全模式 | `pure` 不允许外部 I/O；当前 `strict` 不自动放开新 Provider；真实隔离与失败路径有测试 |
| T10 | 扩展接口 | 新高层 I/O/协议函数不增加任何 HostOp；新 Provider 通过约定的独立注册/版本机制接入 |
| T11 | 兼容/性能 | Windows/macOS/Linux 的支持矩阵真实披露；可定量报告字节访问吞吐、内存增长和 Python/Rust baseline 差距 |
| T12 | 文档与证明 | Memory 状态可导出可读快照；执行状态引用源 Markdown span；不将数据表格误认成内存本体 |

## 14. 需要 ADR 决断而不是隐含假设的开放问题

本 RFC 采用一条**可实施的推荐路线**，但下列决策会改变公开语义，须单独冻结：

1. **页语义**：推荐 64 KiB 页、只增长；是否与外部目标标准保持一致，预算如何计入已保留与已提交物理内存。
2. **Memory 的值/调用传递**：推荐复制引用保持身份，区域可达则存活；禁止隐式跨线协议序列化。
3. **Memory 引用寿命**：推荐首版只在一次执行期间有效，采用自动回收或至少结束时回收；内部块分配是 stdlib 职责。
4. **Place AST**：推荐首版只增 Local + Memory Index；其他集合的索引赋值须另行评议。
5. **OS Resource 最小 ABI**：是否先使用现有插件注册机制包装，而不立即新增第二套并行插件协议。
6. **跨平台支持范围**：纯计算 API 保持统一；系统资源能力按平台明示 availability，不能假定所有设备/系统调用均存在。
7. **实验数据**：R2 执行效率可能较低，是否加入 32/64 位宽读写及优化编译由实测结果决定，而非预设几十种关键字。

## 15. 最终建议与决策摘要

**建议通过的架构选择：**

- **语言核心**：保留现有托管值与控制流，新增**显式、多区域、可增长的字节 Memory**；用现有索引表达式扩展可写位置，不创建新的 Markdown 语法层。
- **内存管理能力**：`Memory` 区域由 Runtime 提供并保护区域边界；`malloc/free`、块布局、链表、树、二进制编码等由 `.mq.md` 标准库自己构造。
- **系统能力**：独立、授权、可替换的 `Resource` 边界；标准库在 Marqdo 中组合 I/O，OS 的最后一跳仍由可信本地 Adapter/Provider/编译后端承担。
- **扩展性**：不为每个库函数增加 Rust `HostOp`；只有新增*真正不可由现有原语表达*的硬件/OS 能力，才需要扩展适配器。
- **安全性**：区分区域边界安全、块级内存安全、进程隔离和 OS 权限；不能用“沙盒”一词掩盖缺少的保证。
- **长期演进**：以此作为实现自主数据结构、字节码 VM、优化执行器与量子/科学计算后端的基础，但不许声称三个内存原语就能自动产生 GPU/QPU 加速。

**核心结论：** 如果“摆脱宿主语言依赖”指的是**程序逻辑、标准库算法和高级系统功能不依赖宿主语言来实现**，这条路线可以达成；如果指的是**无需任何底层可信机器代码和操作系统接口即可访问硬件**，则不可能。对真正的独立编程语言而言，恰当目标是**自己定义计算、自己构建高层库、清楚且可扩展地跨越不可消除的系统边界**。
